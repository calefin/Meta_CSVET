# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Plumora Gen — SaaS platform for breeders of exotic/domestic birds and racing pigeons. Modules: flock management, breeding (pairs/cages/clutches/offspring), health, vaccination, medication, feeding, genetics calculators, pedigree (Wright inbreeding coefficient), competitions, vet telemedicine ("PigeonVet"), a breeder dashboard (aggregated stats + alerts), e-mail marketing campaigns (admin), plantel CSV export, billing (Mercado Pago) with a hard-lockout access gate for lapsed paid subscriptions, admin. See `README.md` for the full module list and `ROADMAP.md` for phase-by-phase status (what's done vs. pending) — check `ROADMAP.md` before assuming a feature is unimplemented or complete.

## Commands

### Backend (`backend/`, FastAPI + Python 3.11)
```bash
pip install -r requirements.txt
python -m alembic upgrade head        # apply migrations
python ../seeds/seed_db.py            # populate species, genetic loci, vaccines, plans
uvicorn app.main:app --reload         # dev server (http://localhost:8000)
pytest                                # run all tests
pytest tests/test_auth.py             # run a single test file
pytest tests/test_auth.py::test_register_and_login   # run a single test
```
Tests use an isolated SQLite DB (`test.db`, created via `Base.metadata.create_all`) with `get_db` overridden in `app.dependency_overrides` — they do not touch Postgres. There is no lint/format command configured for the backend.

### Frontend (`frontend/`, React 18 + Vite + TS)
```bash
npm install
npm run dev        # dev server on :5173, proxies /api -> localhost:8000 (see vite.config.ts)
npm run build       # tsc typecheck + vite build
npm run lint        # eslint, --max-warnings 0
```
No frontend test runner is configured.

### Full stack via Docker Compose
```bash
cp .env.example .env
docker compose up --build    # app at http://localhost, API docs at /api/docs
```
`docker-compose.yml` wires: `db` (Postgres 16), `redis`, `minio`, `backend` (uvicorn --reload, bind-mounted), `celery` (worker via `app.tasks.pdf_tasks.celery_app`), `frontend`, `nginx`. `docker-compose.prod.yml` is the production variant.

## Architecture

### Backend layering
`app/main.py` wires routers only — no business logic. Each domain has a consistent three-file split: `models/<domain>.py` (SQLAlchemy), `schemas/<domain>.py` (Pydantic), `routers/<domain>.py` (endpoints, prefixed `/api/...`). Cross-cutting logic that doesn't fit a single router lives in `services/` (e.g. `services/pedigree_gen.py` for recursive pedigree/Wright coefficient, `services/zootechnical.py` for fertility/performance indices, `services/genetics/` for the trait calculators).

Auth is JWT via `app/dependencies.py`: `get_current_user` decodes the bearer token and loads the user; `require_role(*roles)` wraps it for RBAC. Roles are `admin` / `vet` / `breeder` — this is the whole authorization model, there is no finer-grained permission system. Settings (`app/config.py`) are pydantic-settings loaded from `.env`; `Settings.database_url` URL-encodes user/password to survive special characters.

**Alembic note:** migration files under `backend/alembic/versions/` are tracked in git (this was fixed after `.gitignore` previously excluded them, which meant `git pull` on the VPS never brought new migrations — always confirm a newly generated revision file is actually `git add`ed). Schema changes to `app/models/` need a generated revision (`alembic revision --autogenerate -m "..."`) before `alembic upgrade head` will create/alter tables — **always review the autogenerated file**: a new `NOT NULL` column on a table that already has rows needs an explicit `server_default=...` (autogenerate frequently omits it), and a new enforced invariant (e.g. a required foreign key/status) on existing rows may need a hand-written data backfill `op.execute(...)` in the same migration, not just the schema change. `alembic/env.py` builds its own engine from `settings.database_url` (not from `alembic.ini`'s `sqlalchemy.url`, which is a dev-only fallback) — this was a deliberate fix to avoid `configparser` interpolation issues with special characters in the DB password and `set_main_option` conflicts.

### Genetics calculators
Two independent, non-shared engines:
- `services/genetics/calculator.py` — psittacine (parrot-family) multi-locus calculator: modes `re` (recessive), `se` (sex-linked), `do` (dominant), `in` (incomplete dominant), `cd` (codominant), and multi-allelic. Includes sex-linked crossover rates (cin=7%, ych=3%, ino=30%).
- `services/genetics/pigeon_calculator.py` — pigeon-specific ZW sex-chromosome system: color+dilute haplotypes, epistasis (spread/red), wing pattern, feathered feet, plus an automatic clinical alert for homozygous barless (visual risk).

Genetic loci are species-specific seed data under `seeds/genetics/` (one file per species), loaded by `seeds/seed_db.py`. Only Calopsita (cockatiel) and pigeon loci are seeded today; other species listed in the README (Agapornis, Periquito, Rosela, Canário, Forpus) have routers/UI but no genetic loci seeded yet — check `ROADMAP.md` §6.4 before assuming a species' genetics calculator has real data.

### Immutability convention
Vaccination and medication records are append-only by design: no update endpoint exists, only create/delete. Each vaccination record gets a SHA256 hash as tamper-evidence (no blockchain). Don't add an edit/update endpoint for these without checking `ROADMAP.md` — this is an intentional compliance/audit decision, not an oversight.

### Frontend structure
`src/pages/` is split by role: `breeder/` (the main app), `vet/` (PigeonVet queue), `admin/`. `src/router/index.tsx` is the single source of truth for routes and gates them with `PrivateRoute` (auth required) and `RoleRoute` (role allow-list) wrapping `useAuthStore` (Zustand). All HTTP calls go through `src/services/api.ts` (axios) — there is no per-page fetch logic. Server state/caching is TanStack Query; client/UI state is Zustand (`store/`); forms use React Hook Form + Zod. i18n strings live in `src/locales/{pt-BR,en-US}` and PT-BR is the default locale — new user-facing strings need both files updated. Path alias `@/*` maps to `src/*` (configured in both `vite.config.ts` and `tsconfig.json`).

### Async/background work
Celery (`app/tasks/`) handles PDF generation (`pdf_tasks.py`, pedigree export via ReportLab), notifications (`notification_tasks.py`, e.g. PigeonVet call-opened emails to `calefi@csvet.com.br` and the breeder, via Resend), and marketing campaign sending (`marketing_tasks.py`, via Gmail SMTP — a deliberately separate provider/credentials from the Resend-based transactional emails). Redis is the broker.

**Celery gotcha (caused a real production bug, now fixed):** the worker is started as `celery -A app.tasks.pdf_tasks.celery_app worker` (see `docker-compose.yml`), which only imports that one module by default. `pdf_tasks.py` is therefore the **only** place a `Celery(...)` instance may ever be constructed — every other task file (`notification_tasks.py`, `marketing_tasks.py`) must `from app.tasks.pdf_tasks import celery_app` instead of creating its own. `pdf_tasks.py`'s `Celery(...)` call also needs every sibling task module listed in its `include=[...]` argument, or the worker process never imports that module and its `@celery_app.task`-decorated functions are invisible to it ("Received unregistered task", silently dropped — this previously broke password-reset emails and PigeonVet notifications with no visible error). Adding a 4th task file requires updating `include=[...]` in `pdf_tasks.py`, not just importing `celery_app`.

### Subscription access gate
`app/dependencies.py::check_subscription_active` hard-blocks (HTTP 402) any `role="breeder"` user whose current paid plan (`Plan.name != "free"`) has no `Subscription` row with `status="active"` and `current_period_end >= now()`. Free plan, no plan at all, and non-breeder roles are always exempt — this never deletes data, only blocks access. It is applied **per-router, opt-in**, via `dependencies=[Depends(check_subscription_active)]` passed to `app.include_router(...)` in `main.py` — **not** inside `get_current_user` itself. This means a new router added to `main.py` is unprotected by default unless someone remembers to add that `dependencies=` kwarg; when adding a new breeder-facing router, check whether it should be added to the `_subscription_gate` list in `main.py`.

## Conventions worth knowing

- Roles are exactly `admin`, `vet`, `breeder` — enforced both in backend `require_role()` and frontend `RoleRoute`; keep both in sync when adding role-gated features.
- CPF validation (`app/utils/cpf.py`) implements the official Brazilian check-digit algorithm — no external service dependency.
- Timestamps are stored in UTC in the DB; timezone conversion/formatting happens in the frontend, not the backend.
- Plan limits (free/basic/pro/premium — bird count, claudogram/month, PigeonVet/month) are enforced in the relevant routers, not centrally; check the README's plan table when changing limit logic. This is separate from the subscription *access* gate above — a 402 from a plan limit ("bird cap reached") and a 402 from a lapsed subscription look identical over HTTP; don't assume every 402 means "billing is broken" (the frontend interceptor currently conflates them — see ROADMAP known-issues if fixed).
- Billing provider is **Mercado Pago** (`app/services/mercadopago_client.py`), not Stripe — Stripe was fully removed (package, config, `Subscription.stripe_sub_id`). The official `mercadopago` SDK's `sdk.preference()`/`sdk.preapproval()`/`sdk.payment()` are factory methods whose `.create()/.get()/.update()` return `{"status": <http_status>, "response": <dict|None>}`, not a typed object.
- PUT/update endpoints that support partial updates must use `body.model_dump(exclude_unset=True)`, not `exclude_none=True` — the latter can't distinguish "client explicitly sent `null` to clear this field" from "client omitted this field", silently dropping intentional null-clears (e.g. unassigning a cage). See `routers/breeding.py`'s `update_breeding`/`update_clutch`/`update_offspring` for the corrected pattern.
